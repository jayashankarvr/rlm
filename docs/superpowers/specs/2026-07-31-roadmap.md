# Roadmap: Act-in-Place Guard, Preventive Tier, and the Path Upstream

**Date:** 2026-07-31
**Status:** Sequence frozen (design discussion)
**Supersedes:** intervention mechanics in `2026-05-30-freeze-guard-design.md` §6
(the engine/sampler architecture and never-kill policy stand)

## Why Phase 0 exists

The current effector migrates a single victim PID into a private `guard-<pid>`
cgroup and freezes that. Three defects, one root cause:

1. **Single-PID freeze is wrong for multiprocess apps.** Freezing one Firefox
   process leaves its dozens of siblings allocating; pressure doesn't fall.
2. **Migration fights everything else.** `rules.rs` grew `guard_held` plumbing
   solely so the RulesEnforcer wouldn't yank guard-held PIDs back out of
   `guard-<pid>`. The subsystems contend because migration creates a second
   home for the process.
3. **Migration destroys systemd's placement** and never restores it.

Acting in place — freeze/cap the cgroup the process already lives in — deletes
all three at once. The headline is not "fixes a bug"; it is **"deletes a
subsystem"**: `guard-<pid>`, the `unlimit` migration machinery, and the
`guard_held` plumbing all go.

## Phase 0 — Act in place (correctness; blocks everything else)

Two co-equal deliverables: `resolve_target` and the restore journal.

### `resolve_target` (pure function, first-class deliverable)

Input: victim PID, its `/proc/<pid>/cgroup` path, protect-list, unit-management
facts. Output:

```
struct Resolution {
    cgroup:    PathBuf,            // target to act on
    verdict:   Freeze | CapOnly,   // freeze permitted, or cap-only
    coverage:  Full | Partial,     // fed to the policy engine, not just logs
    mechanism: Unit | Raw,         // how to act on this target
}
// or None: culprit is outside the acted-on universe
```

Contract:

- **Ceiling is a containment predicate over a set of permitted roots:** the
  target must be strictly below `app.slice` **or** strictly below rlm's own
  delegated subtree (`user@<uid>.service/rlm/` — where `app-<exe>` rule groups
  and manual limits live; a single-path ceiling would make every rule-limited
  process invisible to the guard and `mechanism: Raw` unreachable). A culprit
  outside both roots (stray user service, something under `session.slice`)
  resolves to `None` — never walk sideways or upward past a permitted root.
- **Precedence: safety over coverage.** Preferred target is the `*.scope`
  boundary (whole process tree). If that scope contains a protected exe
  (single-scope terminals: alacritty, kitty — the shell and the runaway script
  are siblings in the same leaf), degrade: **cap-only, never freeze**. There is
  no deeper cgroup to fall back to, creating a child under a systemd-owned
  scope violates single-writer, and migrating out resurrects what this phase
  deletes. `memory.high` on the shared scope is benign for the terminal — its
  anon footprint is tiny relative to the budget (see cap sizing).
- **`coverage` is decision-path, not cgroup-shape:** `Partial` ⇔ the safety
  rule forced degradation from the preferred target (protected-exe shrink,
  cap-only verdict, ceiling → leaf fallback). Child cgroups under the resolved
  target do NOT reduce coverage — the v2 freezer is hierarchical; freeze
  propagates to all descendants. A tree that escaped its scope (daemonized
  child, `systemd-run`) is undetectable without a PPID walk and classifies
  Full; it self-corrects within one hold cycle because the escapee becomes the
  next victim.
- **Policy engine consumes `coverage`:** on `Partial`, the global escalation
  gate shortens (to ~one tick) — a fraction of the intended relief was
  applied; don't sit out a full `freeze_hold` before acting again.
- **`mechanism`:** unit-managed targets (`*.scope`, `*.service`) act via
  D-Bus; rlm-created cgroups (`app-<exe>` rule groups) act via raw writes.
  Both paths exist in the effector regardless.
- **Two placement models coexist after Phase 0, deliberately:** the guard
  acts in place; `rules.rs` still migrates matching PIDs into `rlm/app-<exe>`.
  That migration is the *point* of a rule (a persistent home with limits),
  not the defect Phase 0 removes (a transient second home fighting the
  process's real one). The guard treats rule cgroups as just another
  resolvable target via the second permitted root.

Pure and testable without root, matching the existing engine architecture.

### Effector: D-Bus, not fork+exec

Both `systemctl --user freeze` and `notify-send` are fork+exec — which
allocates, faults, and can block in reclaim, i.e. the intervention mechanism
is itself pressure-sensitive. Unacceptable in the storm path. Therefore:

- **zbus in Phase 0.** `FreezeUnit`/`ThawUnit` for freeze;
  `SetUnitProperties(runtime=true)` for `memory.high` on unit-managed targets.
  This is the one place the lean dependency tree spends, and it makes Phase
  4's notification-with-actions nearly free (same connection).
- **Connection opened at daemon startup**, kept warm, reconnected on idle —
  never established at intervention time.
- **Degradation path:** `FreezeUnit` with a short timeout → fall back to raw
  `cgroup.freeze`. Raw freeze on a systemd-owned scope is cosmetically
  impolite (unit state won't say frozen) but harmless and reversible.
- **Restore is mechanism-independent.** The journal is written before the
  act, but the mechanism is only known *during* it (`FreezeUnit` may time out
  and degrade to Raw) — so a recorded mechanism can be wrong, and
  thaw-via-record would strand exactly the case the field was meant to save.
  Instead: restore does `ThawUnit` best-effort (reconciles systemd's state
  when the bus works), then a raw `cgroup.freeze=0` write unconditionally.
  Raw thaw of a unit-frozen cgroup works; thawing a thawed cgroup is a no-op;
  `memory.high` restore is a raw write in all cases anyway. The journal's
  `mechanism` field is diagnostic, not load-bearing.
- **Interlock (documented, benchmark accordingly):** `FreezeUnit` transits
  the user bus and `systemd --user`. Verified placement on a live Ubuntu
  26.04 GNOME session (2026-07-31): `dbus.service` runs in `session.slice` —
  covered by Phase 1's chain as specified. `systemd --user` runs in
  `user@.service/init.scope` — above the cap but *outside* `session.slice`,
  so the chain as originally specified leaves the second hop of every
  `FreezeUnit` call unprotected; Phase 1 must include a `memory.min` drop-in
  for the user manager's `init.scope` (user-level `init.scope.d/`). Phase 0's
  mechanism *works* alone; it becomes reliable under storm once Phase 1
  lands. Do not benchmark Phase 0 in isolation and conclude D-Bus was a
  mistake.

### Restore journal (write-ahead, co-equal deliverable)

Persisted to disk (in-memory state cannot survive SIGKILL). Write-ahead:
append + fsync **before** mutating. A crash between record and mutation leaves
a harmless stale entry; the reverse leaves a permanently throttled process.

Entry: `{cgroup_path, cgroup_inode, prev_high, our_high, mechanism}`.
File header: `boot_id` (`/proc/sys/kernel/random/boot_id`).

Restore guards, on sweep:

- **Boot ID mismatch → discard all entries.** No cgroup state survives reboot.
- **Inode mismatch → skip entry.** Scope names are reusable; kernfs node IDs
  are unique within a boot. Never write into a same-named stranger.
- **`memory.high != our_high` → skip entry.** Someone (user, systemd) changed
  it since; don't clobber. Also makes stale write-ahead entries self-dropping.
- **Thaw mechanism-independently** (ThawUnit best-effort, then raw write —
  see effector).

Atomic-rename compaction on clean shutdown.

### Cap sizing

`memory.current` is the wrong denominator — it includes page cache; a cap at
90% of a cache-heavy scope is absorbed entirely by cache reclaim and throttles
nothing. Size off **`memory.stat` `anon` + `memory.swap.current`** (parity
with the RSS+swap victim scoring). Cache reclaim still happens as a side
effect — desired — it just isn't the entire effect. This also preserves the
shared-terminal property: the emulator's anon footprint sits well inside an
anon-derived budget.

### Also in Phase 0 (falls out of the same work)

- **Delete** `guard-<pid>` creation, `unlimit` migration, `guard_held`
  plumbing in `rules.rs` and its tests. Sweep is retargeted at journal replay.
- **Protect-list matching on resolved identity** (cgroup path /
  `realpath(/proc/<pid>/exe)` basename), not truncated `comm`. The shipped
  builtin list is safe today (longest: `kwin_wayland`, 12 chars); the defect
  is the user-extension path — `protect: [gnome-control-center]` silently
  never matches at 15-char `comm`.
- **RulesEnforcer skips frozen targets** — read `frozen` from the target's
  `cgroup.events` (kernel's view; the freeze may not be ours) rather than
  tracking state internally.

**Gate:** a frozen-then-thawed Firefox is still in `app-*.scope` afterward
with its original `memory.high` intact; kill -9 the daemon mid-intervention,
restart, and the journal replay restores the same.

## Phase 0.5 — Minimal harness

Built before further features; grown into the Phase 6 matrix later.

- **Stall probes** (the detector comes before the reproducer):
  - *Locked control:* 50ms sleep loop, pre-faulted + mlocked (its own pages —
    the caller may), records elapsed-vs-expected drift and
    `/proc/self/schedstat` field 2 (runqueue wait). Drift here is pure
    scheduling latency.
  - *Unlocked treatment:* same loop, touches a small file-backed + anon
    working set each iteration, additionally records `maj_flt` from
    `/proc/self/stat`. Its fault count directly answers "does
    `session.slice`'s working set stay resident under storm" — Phase 1's
    claim. (An mlocked probe never major-faults; the pair exists because one
    process cannot measure both.)
  - (unlocked − locked) drift isolates the memory-induced stall component:
    "Phase 1 reduced fault stalls by X and left scheduling untouched."
  - *Third instance, `app.slice`:* same unlocked design, placed via
    `systemd-run --user` (default slice). This is the probe that sits *under*
    Phase 1's dynamic cap and measures foreground throttling — the number the
    Phase 1 tradeoff requires. The session pair cannot see it: they live in
    `session.slice`, outside the cap. Cheap now; annoying to retrofit after
    baselines are recorded against a two-probe layout.
  - Placement: `systemd-run --user --slice=session.slice` for the session
    pair — same reclaim treatment as the compositor without writing into a
    systemd-owned `cgroup.procs`.
  - *Observer effect (documented):* the probes draw from the same
    `memory.min` budget they measure. Negligible at a few MB; scales badly if
    a probe ever grows.
- One synthetic memory-hog reproducer in a VM. Metrics: probe drift
  decomposition, PSI integral over the event. Input-to-photon waits for
  Phase 6.

## Phase 1 — Preventive tier (best effort-to-value in the project)

- MGLRU `min_ttl_ms` — oneshot unit, conditional on `/sys/kernel/mm/lru_gen/`,
  default 1000, configurable.
- Session protection drop-ins: `memory.min` on `session.slice` **plus the
  ancestor chain** (`user-.slice.d/`, `user@.service.d/`) so it is effective —
  and so the Phase 0 D-Bus path survives storms. The chain must also cover
  the user manager's `init.scope` (see the Phase 0 interlock — verified
  outside `session.slice` on 26.04).
  **Sizing discipline — the chain carries sums, not a value.** On
  overcommitment the kernel distributes a parent's protection among children
  proportionally; the effective floor at any node is bounded by its share of
  the parent, so copying one measured number up the chain silently dilutes
  every leaf, and the failure presents as "`memory.min` doesn't do much,"
  not as a misconfiguration. Therefore: measure per protected child, derive
  each leaf floor from its measurement (never a generous round number —
  `memory.min` is a floor, not a grant, and a tight floor bounds what a
  leaking protected process can shield; see Named limitations), then **sum
  upward**: each ancestor ≥ Σ of its protected children. The sum has grown
  since first specified — `session.slice` now holds the compositor, `dbus`,
  `rlm-guard` (post placement fix), and the harness probes;
  `user@.service` must carry `session.slice` + `init.scope`. `rlm doctor`
  verifies the sum invariant at every level (this implies — and is stronger
  than — monotone non-decreasing toward the root) and flags any configured
  value substantially above its measurement.
- **Daemon placement:** `rlm-guard.service` currently defaults to
  `Slice=app.slice` (verified: `Delegate=no`, `MemoryMin=48M`) — the
  preventive tier throttles the thing implementing it, and the existing
  `MemoryMin` is inert because app.slice carries no ancestor chain. Fix: set
  `Slice=session.slice` in the unit file. The guard *is* session-critical
  infrastructure, which is what `session.slice` is reserved for — the bus and
  the compositor already live there — and its floor then rides the same
  chain. Interacts with the subtree-hosting question below.
  *Upstream justification (written down now, so it isn't improvised in a bug
  thread later):* `session.slice` is conventionally the session manager's
  territory, and a third-party daemon there is exactly what a GNOME/systemd
  reviewer will question at MIR. The argument: the guard is the mechanism
  that keeps the session responsive under pressure; its failure under
  pressure is the failure mode the package exists to prevent; and
  `app.slice` placement demonstrably (verified, 26.04) renders its
  `MemoryMin` inert. Session-critical infrastructure the session depends on
  — `dbus.service`, pipewire's units — already lives there; the guard is in
  that category, not the app category. (This replaces the dropped
  mlock item: you cannot mlock another process's mappings — `process_mlock`
  never merged; `process_madvise` accepts `MADV_WILLNEED` but requires
  `PTRACE_MODE_READ_FSCREDS` + `CAP_SYS_NICE` since 5.12, unusable
  unprivileged.)
- Dynamic `memory.high` on `app.slice` = MemTotal − R, R from measured session
  working set (daemon-maintained). **Known tradeoff:** when the cap binds,
  reclaim pressure lands proportionally on all children — the foreground app
  gets throttled alongside the background hog, and the user experiences the
  preventive tier as "the app I'm using got slower." The counter-measure
  (`memory.low` on the focused app's scope) requires focus tracking, a real
  dependency deferred past Phase 1. The Phase 0.5 harness must measure
  foreground impact so this tradeoff is a number, not a vibe.
- **The cap has the same blind spot `resolve_target` just fixed:** rule
  cgroups live under `user@<uid>.service/rlm/`, outside `app.slice` — so a
  user who manually limits their heaviest app has quietly exempted it from
  the tier that reserves headroom. Capping the common ancestor
  (`user@.service`) dynamically is unreachable: its attributes belong to the
  *system* manager, not the user manager. Resolution, layered:
  1. *Static backstop (reachable now):* the preset package ships a
     `MemoryHigh=90%` drop-in on `user@.service` — systemd accepts
     percentages of physical RAM in unit files, so "static" doesn't mean
     "can't scale to the machine." Covers everything including `rlm/`;
     coarse, but it closes the exemption. Note the backstop and the dynamic
     `app.slice` cap **nest**: `memory.high` applies reclaim pressure
     independently at each level rather than min-combining. Presumed benign —
     a harness question, not an assumption.
  2. *Candidate real fix (mechanics verified live on 26.04; decide at
     Phase 1):* relocate rlm's
     subtree under `app.slice` via a `Delegate=yes` unit. That collapses the
     permitted-roots set back to one and puts rule cgroups under the dynamic
     cap. **The hosting choice conflicts with daemon placement (above):**
     `Delegate=yes` on `rlm-guard.service` itself is one line *only if* the
     daemon stays in `app.slice` — which leaves it under the cap,
     unprotected. With the daemon in `session.slice` (as it should be), the
     subtree needs a **separate `Delegate=yes` holder unit in `app.slice`** —
     a third unit in the package, and it **must run a keeper process**:
     verified live (26.04) that a `RemainAfterExit` oneshot with
     `Delegate=yes` stays `active` but loses its cgroup the moment its
     process exits. So the holder is a trivial long-running unit (`sleep
     infinity` or a tiny `rlm-hold` binary). Lifetime coupling: default
     `KillMode=control-group` means stopping the holder kills every limited
     app, so the holder sets `KillMode=process` — and restart-with-residents
     is **verified safe** (26.04, live): a PID migrated into a delegated
     child cgroup survives `systemctl --user restart` of the holder, in
     place, child cgroup and settings intact.
  3. If (2) fails investigation, (1) stands and the doc names the residual:
     rule-limited apps see only the static backstop, not the dynamic cap.
- **zram ships in the preset package, ranked above `watermark_scale_factor`
  on effect.** On a swapless machine only file pages are reclaimable, so anon
  growth goes straight to OOM with the thrash window compressed to nothing;
  compressed swap gives reclaim somewhere to put anon pages at RAM speed.
  Fedora enables it by default; Ubuntu doesn't. Static configuration
  (zram-generator config), so it belongs with the sysctl preset.
  **Interaction to revisit:** rlm's limit policy sets `memory.swap.max=0` on
  managed cgroups — chosen to prevent disk-thrash, but it also denies zram to
  exactly the apps rlm manages. Once the preset lands, swap.max for managed
  cgroups should become bounded-nonzero (zram-backed swap is the fast path,
  not the thrash path); re-evaluate with harness numbers. Cheap: the unlimit
  path already restores `max` (cgroup.rs:373), so this is one constant plus a
  config knob, not new machinery.
- **sysctl preset (`vm.watermark_scale_factor`, `vm.min_free_kbytes`) + zram
  ship as a separate binary package**, not core: system-wide and opinionated;
  a distro can seed one and not the other, which materially eases the core
  package's MIR.

## Phase 2 — Detection

- PSI trigger + `poll()` replacing the fixed 1s timer; zero wakeups when calm.
  **Feature-test, don't version-check:** attempt the trigger install, fall
  back to the timer on `EPERM`/`EINVAL`, `rlm doctor` reports the active
  mode. (Unprivileged triggers need ~6.9+, but Ubuntu backports aggressively.)
- Adaptive enumeration — scan only when level > Calm; walk the cgroup tree,
  not all of `/proc`.
- I/O pressure — same parser on `/proc/pressure/io`; remedy is `io.latency`
  on the session, never freeze.
- Suspend/resume guard — discard the first samples after a monotonic gap;
  PSI is garbage post-resume.

## Phase 3a — Attribution, causal signals first

- Allocation rate (Δrss/Δt) + `pgmajfault` deltas from `memory.stat`. No
  persistence, no baselines. These are *causally* correct — they identify who
  is generating pressure now.

**Gate:** on a machine running Firefox + a runaway script, the script gets
picked. That is the differentiator; it is a harness scenario.

## Phase 3b — Persisted baselines, only if 3a shows a gap

- Rolling p95 per executable, plain JSON with atomic rename (not sled —
  effectively unmaintained), bounded size, drift protection. Built only if
  harness numbers show the anomaly heuristic adds anything over 3a.

## Phase 4 — User agency (the upstreamable piece)

- `org.freedesktop.Notifications` with actions — Resume / Keep paused / Kill.
  Same zbus connection Phase 0 paid for; replaces `notify-send` entirely.
- Hold freeze until PSI actually falls; timer as ceiling, not policy.
- GUI: guard status page — live PSI, intervention history, learned baselines;
  manual-limit path kept visibly separate.
- Codebase split: deliberate limits (CLI/GUI) vs background policy — modules
  are already separate; remaining work is the config surface.

## Phase 5 — Hardening

- `find_delegated_cgroup` verifies write access and `cgroup.subtree_control`;
  fail loudly at startup.
- `rlm doctor` checks every Phase 1 knob and reports what's missing, plus
  PSI-trigger mode (Phase 2).

## Phase 6 — Evidence, then upstream

- Grow the Phase 0.5 harness into the full matrix: memory hog, parallel
  build, browser tab storm; freeze duration, PSI integral, input-to-photon,
  false-positive rate; stock Ubuntu vs stock+Phase 1 vs full rlm. Write up
  the numbers. No numbers, no conversation.
- Split the upstream asks — notification-with-actions goes to GNOME/systemd
  on its own; it's wanted and small.
- Package path: Debian packaging → PPA → universe → MIR, positioned as
  complementary to systemd-oomd, never a replacement.

## Named limitations (by design, not omission)

- **Compositor-as-culprit is unhandled.** A leaking compositor (bad shell
  extension) is on the protect-list, so the guard never acts on it and the
  machine eventually dies. Freezing the compositor kills the session UI —
  worse than the freeze it would prevent — so there is no sensible action for
  an unprivileged per-user daemon here. Phase 1's `memory.min` on
  `session.slice` *amplifies* this case — it protects the leaker's pages and
  pushes reclaim onto everyone else — but the amplification is bounded by
  sizing, not structural: `memory.min` is a floor, not a grant. A compositor
  leaked to 8 GB with a floor sized to a measured 1.2 GB has 1.2 GB protected
  and 6.8 GB reclaimable like anyone else's. Severe amplification requires a
  floor set generously "to be safe" — hence the Phase 1 sizing discipline
  (derive from measurement, `doctor` flags configured ≫ measured). The
  residual — the machine still eventually dies if the leak outruns reclaim —
  is accepted; the honest mitigation is detection-and-notify ("gnome-shell
  has grown to X GB — an extension may be leaking"), cheap on Phase 3a's
  signals.

## Explicitly not doing

- Per-app static min/max in the guard (GUI-only, user-initiated — settled).
- CPU freeze policy — `cpu.weight` suffices; freezing on CPU pressure is wrong.
- Its own scheduler; sched_ext is a separate universe.
- Kernel patches — everything above is userspace plus sysfs.
- Non-systemd init support.
- `process_madvise` fault-in during recovery — exists, but the permission
  model excludes an unprivileged per-user daemon (see Phase 1).
