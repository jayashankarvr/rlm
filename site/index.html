Keep one app from taking the whole machine

rlm sets memory, CPU and I/O limits on your own Linux processes, without root, from the terminal or a desktop app. Its optional guard freezes or caps a runaway app under memory pressure, instead of letting the desktop lock up.

What it does

  • Start a program with limitsrlm run --memory 2G --cpu 200% -- cargo build runs the build with at most 2 GB of memory and two cores.
  • Limit something already runningBy PID, by name, a list of PIDs, or a whole application with every process under one shared limit.
  • Profiles and rulesFour built-in presets plus your own, and rules that apply to an app every time it starts.
  • A desktop apprlm-gtk does the same from a GTK window: pick an app, set limits, apply.
  • An optional guardrlm-guard watches memory pressure and freezes or caps the app that is growing, never killing it.

rlm uses cgroup v2 through systemd's per-user delegation, so it needs no root and only ever touches your own processes.

What it is not

  • Not a replacement for systemd-oomd or earlyoom. Those kill processes; rlm pauses and slows them. You can run both.
  • Run as your user, it has no effect on processes of other users or of root.

Not yet

  • Protecting the desktop session's own memory with a memory.min chain.
  • Event-driven pressure triggers. The guard samples once per second.
  • Notifications with Resume or Keep paused actions. Today the guard can send a plain warning when pressure rises.
  • A system-wide mode for other users or system services.

Install

  1. Add the signing key 
    sudo install -d -m 0755 /etc/apt/keyrings
curl -fsSL https://jayashankarvr.github.io/rlm/rlm-archive-keyring.gpg | sudo tee /etc/apt/keyrings/rlm.gpg >/dev/null
  2. Add the repository 
    echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/rlm.gpg] https://jayashankarvr.github.io/rlm stable main" | sudo tee /etc/apt/sources.list.d/rlm.list
  3. Install 
    sudo apt update
sudo apt install rlm rlm-gtk

The desktop app, rlm-gtk, needs Ubuntu 24.04 or Debian 13 or newer; rlm alone works from Ubuntu 22.04 and Debian 12. Updates arrive with apt upgrade.

Key fingerprint: C7E1 E11F ED31 3EDB 9A60 9BD7 41F3 0081 BB8A BEC2. The same key is in the source at dist/apt/rlm-archive-keyring.asc.

Download the .rpm files from the latest release, then:

sudo dnf install ./rlm-0*.rpm ./rlm-gtk-0*.rpm

rlm-gtk needs Fedora 40 or RHEL 10 or newer.

With Rust 1.87 or newer:

cargo install rlmctl

This installs rlm and rlm-guard. The desktop app is not on crates.io, because it needs the GTK 4 and libadwaita development headers; install it from a distribution package or from source. With cargo you also set up cgroup delegation yourself.

git clone https://github.com/jayashankarvr/rlm
cd rlm
cargo install --path cli        # rlm and rlm-guard
cargo install --path gtk-gui    # rlm-gtk, needs GTK 4 and libadwaita headers
./install-desktop.sh            # desktop entry and icon

On Debian and Ubuntu the headers come from libgtk-4-dev libadwaita-1-dev pkg-config. Set up cgroup delegation yourself.

After installing

  1. Make sure the memory, cpu and io controllers are delegated to your user. The packages do this for you; for cargo and source installs, see cgroup delegation.
  2. Log out and back in, so your user session picks up the delegation.
  3. Run rlm doctor. It checks cgroup v2, the delegated controllers, memory pressure information, your config file and the guard.
  4. Optional: turn on the guard with rlm guard enable, or with the switch on the Guard page of the desktop app.

After upgrading, restart the guard so the new version runs: systemctl --user restart rlm-guard.

Supported systems

The CLI and the guard run on any Linux with cgroup v2, pressure stall information (PSI) and systemd. The desktop app also needs GTK 4 and libadwaita 1.4 or newer. The release packages install on:

Using the CLI

Limit a running app

# One process, by PID
rlm limit --pid 1234 --memory 512M --cpu 50%

# Every process with this name, each with its own limit
rlm limit --name firefox --memory 2G

# A whole application: all its processes share one limit
rlm limit --application firefox --memory 4G --cpu 75%

# Several PIDs sharing one limit
rlm limit --all-pids 1234,5678,9012 --memory 2G --cpu 50%

# With I/O limits (per second)
rlm limit --pid 1234 --memory 1G --io-read 50M --io-write 20M

# Preview without applying
rlm limit --pid 1234 --memory 512M --dry-run
  • With --application or --all-pids, the processes share the limit: 10 processes with a 4G limit get 4G in total, not 4G each.
  • Sizes accept decimals and B/iB suffixes: 512M, 1.5G, 2GiB and 512MB all work. Memory limits below 8M and I/O limits below 64K/s are refused.
  • CPU is a percentage of one core: 50% is half a core, 200% is two cores.
  • Commands that match more than one process ask for confirmation; --yes skips it, and scripts need it.
  • Your desktop session, shells and audio are on a protect list and are refused unless you pass --force. Processes of other users are always refused.

Run a command with limits

rlm run --memory 1G --cpu 100% -- ./my-program arg1 arg2

# With a profile; flags you add override it
rlm run --profile browser -- firefox
rlm run --profile browser --memory 6G -- firefox

Rules that last

rlm limit --application firefox --memory 4G --save   # limit now and keep the rule
rlm rule list
rlm rule remove firefox

The guard applies saved rules, to running copies of the app and to new ones, so the guard service must be running. rlm unlimit --application firefox drops the live limit and keeps the rule; add --forget to delete the rule too.

Remove limits

rlm unlimit --pid 1234
rlm unlimit --name firefox
rlm unlimit --application firefox
rlm unlimit --cgroup app-firefox

Other commands

rlm status                       # what is limited now, read-only
rlm profiles                     # built-in presets and your profiles
rlm doctor                       # check your setup
rlm export profiles.yaml         # export your profiles
rlm import profiles.yaml         # import profiles

How limits behave

  • A memory limit is a real RAM ceiling. rlm sets memory.max, starts reclaim at 90% of it with memory.high, and turns swap off for the limited app so it cannot spill over.
  • Memory a process used before you limited it stays counted where it was; only new allocations count against the limit. To cap an app's whole footprint, start it with rlm run.
  • rlm run keeps everything the command started under the limit. If a launcher starts the real app and exits, the app stays limited, and rlm prints the name of its cgroup.
  • rlm run exits with the command's exit code, or 128+N if signal N ended it. When the memory limit made the kernel end a process, rlm says so.

Desktop app

Start it with rlm-gtk or from your app menu. It has five pages; Ctrl+1 to Ctrl+5 switch between them.

  • Managed ProcessesWhat rlm is limiting now, with Undo after you remove a limit.
  • Limit RunningPick whole apps to share one limit, or a single process. Apps are listed by memory use.
  • Launch NewStart a program or an installed app with limits.
  • ProfilesThe built-in presets and your own; edit a preset and restore it later.
  • GuardTurn the guard on or off, and see memory pressure, what it is holding and what it did.

The desktop app hides processes on the protect list. Use the CLI with --force if you really need to limit one.

The guard

When memory runs short, Linux usually freezes the whole desktop for minutes and then kills something. rlm-guard steps in earlier and more gently.

  • It acts when apps stall on memory and free memory is below 20% of RAM, or at once when free memory drops below 400 MB.
  • It freezes the app that is growing for 5 seconds, then caps it with a soft limit if pressure stays high.
  • A freeze always ends after those 5 seconds; a cap is lifted after 30 seconds of calm.
  • It never sends a signal to any process, and it holds at most 3 apps at a time.
  • It only acts on your own apps and on the cgroups rlm created.
rlm guard enable    # install the service if needed, enable and start it
rlm guard status    # state, config, pressure, what it holds, recent events
rlm guard test      # what it would do right now, without acting
rlm guard history   # recent freezes, caps and restores
rlm guard disable   # stop and disable the service

The full log is in journalctl --user -u rlm-guard.

Configure it

Every setting is optional. These are the defaults, under guard: in ~/.config/rlm/config.yaml:

guard:
  enabled: true
  trigger:
    psi_some_warn: 10
    psi_some_high: 30
    psi_full_critical: 10
    mem_available_floor_mb: 400
    act_below_available_pct: 20
  timing:
    freeze_hold_secs: 5
    calm_hold_secs: 30
    freeze_cooldown_secs: 60
    sample_interval_ms: 1000
  selection:
    min_rss_mb: 200
    protect: []   # names added to the built-in protect list
  notify: true

With enabled: false the guard stops freezing and capping but still applies your rules. An invalid config stops the guard with a clear error in rlm guard status; fix the file and run systemctl --user restart rlm-guard.

How it stays safe

Can it kill my app?
No, the guard never kills anything. It only pauses the app for a few seconds, or slows it down with a soft memory cap, and it undoes both on its own. One separate case: a hard memory limit you set yourself with rlm limit or rlm run works like any memory limit on Linux, so an app that goes past it is ended by the system, not by the guard.
What if the guard crashes while an app is frozen?
Every freeze and cap is written to a journal before it is applied. On its next start, even one that fails on a bad config, the guard reads the journal and restores the app. On a normal stop it undoes everything before exiting. Only one guard runs per user.
Could it freeze my desktop or terminal?
No. The desktop shell and compositor, Xorg and Xwayland, sshd, systemd, dbus, the audio stack, common shells, the guard itself, common terminal emulators and tmux and screen are never frozen. An app that shares a scope with one of them can only be capped. Add your own names under guard.selection.protect.
Why did it not act when my machine was slow?
It needs your apps to be stalling on memory while free memory is below 20% of RAM, or free memory below 400 MB. Slowness from CPU or disk load does not count. An app hitting a limit you set yourself does not count either: the rest of the system is fine.
How hard is a cap?
Soft. It never goes below 90% of the app's current memory or below 256 MiB, and it never loosens a limit that was already tighter. The app slows down while the kernel reclaims memory; it is not killed.

Profiles and config

Profiles are named sets of limits. Add your own in ~/.config/rlm/config.yaml:

profiles:
  browser:
    memory: "4G"
    cpu: "200%"
  dev:
    memory: "8G"
    cpu: "400%"
    io_read: "100M"
    io_write: "50M"

A system-wide file at /etc/rlm/config.yaml is read first, and yours overrides it. Profile names are not case-sensitive. These presets are built in:

PresetMemoryCPUI/O read / write
Light512M25%none
Medium2G50%50M/s / 25M/s
Heavy4G100%100M/s / 50M/s
Browser4G75%none

Cgroup delegation

rlm writes to cgroups that your systemd user manager owns, so the memory, cpu and io controllers must be delegated to it. The .deb and .rpm packages set this up. For cargo and source installs, run once:

sudo mkdir -p /etc/systemd/system/user@.service.d
printf '[Service]\nDelegate=cpu memory io\n' | sudo tee /etc/systemd/system/user@.service.d/rlm-delegate.conf
sudo systemctl daemon-reload

Then log out and back in, and run rlm doctor to check.
